`SPEC.md` disagree, `SPEC.md` wins. `README.md` owns the analysis history. `METHOD.md` owns the
queries, the date handling, the bootstraps and figure provenance. Implementation details live in code and tests.

Read `SPEC.md` before changing anything a reader sees.

## The analysis is audited. Do not rewrite it.

`lib/analysis.ts` was ported from the Phase 1-3 static build after an audit.
Four properties are load-bearing. Breaking any of them silently corrupts every
number on the page:

1. **Dates are parsed from components into UTC.** Never call `new Date(someString)`
   on a Socrata timestamp. `created_date` is a floating local timestamp with no
   zone; routing it through the host timezone reinterprets it.
2. **Hour and day-of-week extraction stay in the query.** Socrata's
   `date_extract_hh` and `date_extract_dow` read `created_date` as NYC wall-clock
   time, which is the frame the analysis wants. Do not re-derive them client-side.
3. **Denominators come from walking the calendar**, never from counting returned
   rows. Days with genuinely zero complaints must stay in the denominator.
   Night denominators come from `countCompleteNights`; do not assume a uniform 52.
   Both configured ranges yield 52 nights Monday-Saturday and 51 on Sunday.
4. **Row validation rejects and counts. It never coerces.** `Number(null)` and
   `Number("")` are both `0` and both pass `Number.isInteger`, so the explicit
   null and empty-string guards are load-bearing, not defensive noise.

If you change any of these, a test should fail. If none does, add one.

## Absence is a type, not a null

A missing comparison is a variant of a discriminated union — `Comparison`,
`HourlyGap`, `DescriptorExcess`, `IntervalResult` — never `null` and never a
sentinel zero. This is deliberate: the worst defect found in the previous build
was a page that rendered "0.0% higher" when the API returned nothing.

Reading `percentageDifference` without narrowing on `kind` is a compile error.
Keep it that way. When you add a statistic, give absence its own variant.

## No hardcoded findings

Every claim about direction or magnitude derives from the data being rendered.
No chart title, caption, or sentence may assert that weekends are higher, that
Saturday is the peak, or that any figure has a particular value. The peak night
comes from `peakNight`; the direction comes from `Comparison.direction`.

If the data changed and a sentence would become false, that sentence is a bug.

## Product guardrails that are not negotiable

From `SPEC.md`:

- No causal language. The data measures reporting behaviour, not noise.
- Nothing that identifies residents or buildings, or implies neighbourhood quality.

## Dependencies

Charts are hand-rolled SVG. `d3-scale` and `d3-shape` are permitted. Do **not**
add a component chart library (Recharts, Chart.js, visx), a scroll library, an
animation library, or a state-management library. The Phase 4 architecture
decision in `SPEC.md` authorised one framework migration and no more.

## Charts

Follow the data-visualization method already applied:

- **Emphasis form throughout**: one accent hue for the series the section is
  about, de-emphasis gray for context. Not a categorical palette.
- The palette is validated, not eyeballed. Light `#c2410c` on `#fbfaf7`; dark
  `#e2703a` on `#121417`; de-emphasis `#7d7a74` / `#9aa3ad`. Adjacent CVD ΔE 10.9
  light and 13.9 dark; normal-vision ΔE 16.9 and 17.8. Re-run the validator
  before changing any of them.
- Identity is never carried by color alone: direct labels and `stroke-dasharray`
  are the secondary channel.
- Every chart has a visually-hidden table twin. A value must never be reachable
  only by hovering.
- The hour axis is an interval scale over `[0, 24]`, not a point scale over
  `[0, 23]`. The late-night band spans 22:00 to the axis end plus 00:00 to 04:00.
- Gridlines are solid hairlines. Never dashed.

## Theme

Three states: system (the default), light, dark. The dark palette is declared
twice — under `@media (prefers-color-scheme: dark)` scoped to
`:root:not([data-theme="light"])`, and again under `:root[data-theme="dark"]` —
so an explicit choice beats the OS setting in both directions. CSS cannot share a
declaration block between a media query and a plain selector, so the duplication
is deliberate; `lib/theme.test.ts` fails if the two copies drift.

An inline script in the document head applies the stored choice before first
paint. Do not move that into React: applying it after hydration paints the wrong
palette first, which is the flash the whole arrangement exists to avoid.

The toggle is a control, not content, so unlike everything else it is absent
without JavaScript rather than present. A dead button would be worse than none.

The toggle is one button that cycles system -> light -> dark. A cycling button
hides its next state, so its accessible name carries both what is active and what
pressing will do, and the change is announced through a status node — the icon
itself is silent.

The guess input is a segmented control and uses native `<input type="radio">`
with a visually hidden input and a styled label. `role="radio"` on a button needs
a roving tabindex to get arrow-key behaviour; native inputs get it for free.

## Content must survive without JavaScript

Everything is in the DOM and readable with scripting disabled. Scroll effects and
the reveal animation are enhancement only: the server renders visible, and the
transition class is added after mount. Never put `opacity: 0` in a stylesheet
where content depends on JavaScript to become visible.

`prefers-reduced-motion: reduce` disables transitions entirely.
